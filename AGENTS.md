# Інструкції для агентів репозиторію

Цей репозиторій є самостійним і єдиним джерелом коду для Telegram-бота `@ZaskaletaInfoBot`. Усі інструкції нижче обов'язкові для розробки, перевірки та випуску змін.

## Непорушні технічні правила

1. **Хостинг — Cloudflare Workers.** Основний Telegram-бот працює як Cloudflare Worker із точкою входу `telegram-info/src/worker-entry-pilot-v21.mjs` та конфігурацією `telegram-info/wrangler.jsonc`. **Не переносити основний runtime на Docker, Railway, Render, VPS або інший хостинг.** Існуючі ізольовані Docker/QA-інструменти не є хостингом основного бота.
2. **База даних — Cloudflare Durable Objects (SQLite).** Використовувати чинний binding `OUTBOX` і клас `TelegramOutbox`. **Не додавати сторонні бази даних** (PostgreSQL, зовнішній SQLite, Supabase як сховище стану бота тощо). Наявні зовнішні інтеграції, зокрема передавання звітів про помилки, не дають дозволу створювати інше сховище стану користувачів.
3. **Обов'язкові перевірки коду.** Для кожної зміни коду запускати **обидві** команди в каталозі `telegram-info/`:
   ```bash
   cd telegram-info
   npm run check
   npm test
   ```
   Ці перевірки не замінюють додаткові обов'язкові CI, statewide, безпекові та регресійні гейти. Заборонено послаблювати тести для отримання зеленого результату.
4. **Деплой виключно через наявний сценарій.** Основний бот випускати **тільки** командою `npm run release:staging` з каталогу `telegram-info/` **усередині чинного захищеного ручного GitHub Actions workflow** `.github/workflows/telegram-staging-deploy.yml`. Заборонено обходити цей сценарій прямим `wrangler deploy`, автоматичним деплоєм після звичайного push або розгортанням на іншому хостингу. Зберігати reviewed-tree guard, staging/live-перевірки й можливість відкату.

## Перед будь-якою реалізацією

1. Прочитати `ops/subagents/README.md`.
2. Прочитати файл відповідної ролі власника та рецензента, а також застосовні контракти з `ops/subagents/contracts/`.
3. Не починати реалізацію без дійсного Task Contract із чіткими критеріями приймання, `allowed_paths`, `forbidden_paths`, назвою гілки, власником, незалежним рецензентом та переліком обов'язкових перевірок.

## Правила виконання

- `allowed_paths` і `forbidden_paths` є жорсткими межами задачі.
- Виконавець працює в ізольованій гілці/worktree, створеній від затвердженого Controller базового SHA.
- Формат гілок: `agent/<role>/<task-id>-<slug>`.
- Виконавець і фінальний рецензент мають представляти різні ролі.
- **Заборонено писати безпосередньо в `main` або самостійно дозволяти merge.**
- Заборонено отримувати, розкривати, друкувати, логувати, копіювати чи комітити значення секретів.
- Заборонено самостійно виконувати production-реліз або ротацію облікових даних.
- Заборонено послаблювати тести, перевірки reviewed-tree, правила ізоляції, ручні staging/live-гейти чи вимогу фінальної перевірки на телефоні.
- Чинні правила CI, staging, live-верифікації та phone smoke залишаються обов'язковими.
- Зберігати повну ізоляцію Telegram-проєкту від інших проєктів екосистеми Zaskaleta.

Для реального багатоагентного виконання в Codex додатково дотримуватися `ops/subagents/codex/README.md` та чинних контрактів v1.

Якщо обсяг робіт, безпека залежностей, вплив на секрети або наслідки релізу неоднозначні — зупинити виконання зі статусом `BLOCKED`, а не припускати дозвіл.
